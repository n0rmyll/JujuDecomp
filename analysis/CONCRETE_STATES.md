# Concrete state dispatch and first graphics path

Further findings: `FRAME_PHASES.md` records the startup copyright-screen
evidence, resource references, and embedded names for engine/render phases.

This extends `APPLICATION_DISPATCH.md`. Names remain provisional unless
explicitly identified as addresses or values read from the executable.

## Concrete classes

The state constructors receive the game object and game +0xC8. They install
these primary vtables; offsets are bytes from the table base, including the
two zero metadata words.

| Allocation size | Constructor | Primary vtable | Initialize +0x0C | Iterate +0x10 | Finish +0x14 |
| --- | --- | --- | --- | --- | --- |
| 0xEA4 | 0x800CE2C4 | 0x802C73C0 | 0x800CE484 | 0x800CE88C | 0x800CEB2C |
| 0x452C0 | 0x800CEB90 | 0x802C73A8 | 0x800CED44 | 0x800CEDD8 | 0x800CEEC0 |
| 0x32A0 | 0x800FFC58 | 0x802D4274 | 0x80100E54 | 0x80101E6C | 0x801028F4 |

The 0x32A0 constructor also installs a secondary table at object +4,
using primary-table address +0x18. This is evidence of an additional
polymorphic base/member; do not model it as an ordinary one-table object
when later attempting a matching reconstruction.

## Creation and transitions

During game initialization **0x800E414C**, flag-controlled branches allocate
either 0xEA4 or 0x32A0 bytes, construct the object, and store its pointer at
game +0xC4. The call at **0x800E454C** passes this to **0x80213140**, which
activates it. With the two flags at 0x80332680/81 clear, the 0xEA4 branch
is selected. Earlier initialization also uses a temporary 0xEA4 object.

Transition handler **0x800E4608** destroys the previous object at +0xC4,
clears that field, and branches on the finished state's result:

- Result 1: allocate 0xEA4; construct via 0x800CE2C4.
- Result 2: allocate 0x452C0; construct via 0x800CEB90.
- Result 4: enter a larger resource-selection path that can construct
  the 0x32A0 class. The inner selection has not been fully decoded.
- Result 3: takes a separate branch at 0x800E4BA0.
- Other results: follow the default path; do not assign meaning yet.

These numeric return codes are verified branch values, not proven names
such as title/menu/loading/gameplay. The 0x32A0 class is a **gameplay
candidate** based on its broad per-iteration call graph; the other two
classes should retain address/size labels until resource names and behavior
confirm their roles.

## Lifecycle reconstructed in C

`src/recovered/state_lifecycle.c` models two functions:

- **0x802131A0**: if an active pointer exists, call state +0x14, clear the
  pointer, override the returned code with -1 if owner byte +0x10 is set,
  and call owner +0x24 with the result.
- **0x80213140**: finish the previous state, install the requested active
  pointer, and call its +0x0C method; a null requested pointer returns 1.

An unsuccessful initialize result does not itself clear the new active
pointer in this function. The model preserves that detail. Host structs
and callback signatures are analysis abstractions, not original PPC layouts.

## Concrete graphics boundary

The 0x32A0 state's iteration method **0x80101E6C** includes this static
direct-call path:

```text
0x80101E6C (state iteration)
  -> 0x801D8CA8 (shared frame/graphics orchestration candidate)
     -> 0x801877A4
        -> 0x80130478
           store byte 0x48 to address 0xCC008000
```

The final routine is four instructions: load 0x48, load 0xCC010000,
store byte at offset -0x8000, return. Thus the path demonstrably reaches
the GameCube graphics FIFO address, regardless of unresolved SDK names.
This is a **structural call path**, not evidence that every branch executes
on every frame. Both smaller-state iteration methods also call 0x801D8CA8.

The same shared routine eventually calls **0x801877E0**, which reaches
**0x80130B64**. That lower-level routine uses the `gx` global and writes
command/data words to 0xCC008000. It is a useful next boundary for graphics
API identification. Exact original SDK function names have not been assigned.

## Checks and next work

`python3 tools/verify_application_map.py` verifies all three primary tables
against the hash-identified DOL, the literal graphics-store instructions,
and the direct-call chain against `calls.csv`. The CSV is regenerated by
`python3 tools/index_dol.py`; it is an analysis index, not independent
runtime evidence. All recovered C passes host Clang syntax checks.

Next: decode resource names in the 0xEA4 and 0x32A0 initialization paths;
split the 0x32A0 iteration into simulation, UI, audio, and graphics phases;
identify the SDK entry points at the hardware boundary. Dynamic breakpoints
or tracing will be needed to confirm state identities during the working
RVZ's title-to-gameplay transition. No matching rebuild or native port has
been produced yet.
