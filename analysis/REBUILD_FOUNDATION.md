# Executable rebuild foundation

The original binary-derived object baseline now links to an **exact GJUE78
revision 0 DOL**. All 146 existing DTK split objects link successfully with the
local CodeWarrior GC 1.3.2 linker through wibo, using DTK's generated linker
script and object order. `dtk elf2dol` then produces all **3,113,248 bytes** of
the original executable exactly, including its header, initialized data,
exception tables, padding, section locations, BSS metadata, and entry point.

This is an original-object relink, **not a rebuild from recovered C/C++**.
There are **zero recovered-source replacements** in this relink. Every input
unit in this baseline is marked `autogenerated` by DTK. The
objects are derived from the user's local executable; they are not recovered
original compiler objects. No game image, DOL, ELF, split object, or generated
map is added to the repository. No emulator boot or gameplay verification is
claimed.

## Reproduce

The workspace must already contain the revision-checked original executable,
DTK v1.8.4, the generated split objects, and the locally installed pinned
CodeWarrior GC 1.3.2/wibo tools. The existing README describes extraction and
`tools/setup_matching.py`. To generate the original-object split if needed:

```sh
tools/dtk dol split analysis/config.yml analysis/split
```

Then run:

```sh
python3 tools/check_rebuild_foundation.py
python3 -m unittest discover -s tests -p test_rebuild_foundation.py
```

The checker performs a real link and conversion on each run. It reads the
ordered `units` list and `ldscript` from `analysis/split/config.json`; it does
not search the object directory or guess ordering. The generated link command
is equivalent to:

```sh
tools/wibo tools/mwcc/GC/1.3.2/mwldeppc.exe -nodefaults -fp hardware \
  -lcf analysis/split/ldscript.lcf -m __start \
  -o build/rebuild-foundation/baseline.elf \
  -map build/rebuild-foundation/baseline.map \
  <all 146 objects in split-config order>
tools/dtk elf2dol build/rebuild-foundation/baseline.elf build/rebuild-foundation/baseline.dol
```

The placeholder above is descriptive; the Python command supplies every
object as a structured subprocess argument. It records the exact executable
commands in the report. `--output /path/to/directory` selects an isolated
output directory for an independent rerun.

The original input must have SHA-256
`49faf28a7d2e25422c145754ef41b0c8a8dfcd83e688db1c39ecf21f6e34b706`.
The rebuilt DOL must have the same hash and compare equal byte-for-byte. A
wrong input revision, missing object, duplicate object, command failure,
invalid DOL layout, or any file difference fails the checker. A prior success
report is removed before work begins. Original binaries are never modified.

## First recovered-source replacement

The first source integration replaced the 12-byte stop setter at `0x8020F9C8`
with its compiled C object. One source function and 147 binary-derived fallback
objects reproduced the complete original DOL. Its original extracted unit was
excluded, and the map identified the compiled source as the definition placed
in the executable. The manifest-driven build below retains that replacement
and adds the level-name lookup and application iteration.

## Manifest-driven source link

The current build links **three recovered functions / 164 original code bytes**
with **149 binary-derived fallback objects**, producing a byte-identical
**3,113,248-byte DOL**. It uses a small explicit replacement manifest rather than
hard-coded function coordinates in the checker.

```sh
python3 tools/check_source_link.py
python3 -m unittest discover -s tests -p test_source_link.py
```

The default manifest is `analysis/source-link-manifest.json`:

| Unit | Address / size | Compiled source | Relocations |
| --- | --- | --- | --- |
| Stop setter | `0x8020F9C8` / 12 bytes | `src/recovered/application_flag.c` | None |
| Level-name lookup | `0x801042FC` / 28 bytes | Target-layout candidate in `src/matching/routines.cpp` | `R_PPC_ADDR16_HA` and `R_PPC_ADDR16_LO` to `lbl_802CD918` |
| Application iteration | `0x80213584` / 124 bytes | Target-layout candidate in `src/matching/routines.cpp` | Two `R_PPC_REL24` calls and one `R_PPC_EMB_SDA21` load |

Each entry supplies a unique ID, logical split unit name, address, size, linker
symbol, source path, language, defines, and exact expected relocation records.
The checker rejects duplicate IDs/units/symbols/addresses, overlapping or invalid
ranges, unknown fields, unsupported source options, and malformed relocation
contracts. A different source set can be checked with `--manifest PATH`.
`--output PATH` selects a separate build directory. Inputs and generated object
names remain separate for each replacement.

`analysis/source-link-splits.txt` now contains only the section-layout header.
Every source-unit start/end range is generated from the manifest, explicitly
using four-byte alignment. Split syntax follows the
[DTK split configuration](https://github.com/encounter/dtk-template/blob/main/docs/splits.md).
The checker writes a local configuration and split file, then runs DTK into its
output directory. It never edits `analysis/config.yml`, `analysis/split/`, or the
original DOL. Stale files in the output directory are not discovered as inputs:
only units named by the fresh ordered split configuration enter the link.

All three functions were already individually matched. They compile with GC 1.3.2,
`-proc gekko -O4,p -fp hardware -nodefaults`. The stop setter compiles as C with
a preprocessor name mapping to `fn_8020F9C8`; its body remains unchanged. The
lookup compiles as C++ with `TAK_FN=0x801042FC`, selecting the existing target-layout
candidate. This uses the normal 32-bit PowerPC data layout. Its types remain
provisional; the callback-based host semantic model is not compiled into the
executable.

The lookup loads a configuration pointer from the state, reads its index, and
looks up a value in the table at `lbl_802CD918`. That table remains owned by
`auto_07_802ADBA0_data.o`. Its two relocation records target `0x802CD918` with
zero addends, at function offsets 6 and 10. The function checker applies these
relocations and compares every function byte. The real linker independently
resolves the external data reference. The checker verifies the data symbol has
exactly one provider and its linker-map address is unchanged, then compares the
entire DOL including all table bytes.

The ordered link now contains 152 objects: three source replacements plus 149
binary-derived fallbacks. Each containing binary span is divided around its
source replacement; all three extracted target objects are excluded. The checker
fails unless every manifest unit appears exactly once with the expected code
size, no data, and explicit non-autogenerated ownership. All other units must
remain autogenerated. It also requires:

- each compiled function's complete relocated bytes to equal the original;
- every compiled relocation record to equal its manifest contract;
- each extracted target unit to equal the same original function bytes;
- each target symbol to have exactly one global/weak definition, owned by its
  selected compiled source object;
- each relocation dependency to have exactly one provider;
- each function's original address/size and compiled object to match the map,
  along with each dependency's original address and provider;
- every DOL byte to equal the original, including headers, padding and data;
- manifest, template, sources, behavior tests and actual link-input hashes to
  remain unchanged during the build.

The stop setter's exhaustive host test still checks all 256 prior flag values,
adjacent bytes and repeated requests. All three source replacements remain active
in the same successful full-DOL-equal executable link. No original definition
is left alongside an unused matching object.

Outputs remain under ignored `build/source-link/`: generated splits and config,
compiled source objects, the behavior test, `source.elf`, `source.map`,
`source.dol`, command logs and `report.json`. The report now contains a
`replacements` list, applied relocations, data dependency providers, manifest
and all source input hashes, excluded and compiled object identities, every
actual link-input hash, tool/helper hashes, ordered commands and output hashes.
A failed run clears the previous success report before work begins. The pinned
original SHA-256 and full-file equality remain mandatory.

### Direct-call and small-data integration

The application iteration is compiled from `src/matching/routines.cpp` with
`TAK_FN=0x80213584`. Its three relocation records are required exactly:

| Offset | Type | Target | Definition used by the executable link |
| --- | --- | --- | --- |
| 44 | `R_PPC_REL24` | `fn_80283F7C` / `0x80283F7C` | Binary-derived subsystem in `auto_03_8027B5AC_text.o` |
| 48 | `R_PPC_EMB_SDA21` | `lbl_803312F8` / `0x803312F8` | Binary-derived pointer in `auto_09_80330280_sdata.o` |
| 80 | `R_PPC_REL24` | `fn_8020F9C8` / `0x8020F9C8` | `compiled_application_flag.o` |

This verifies a compiled-source caller reaching the already compiled source
setter, a source-to-binary function call, and a small-data load in the same
full-DOL-equal executable. The iteration's virtual calls remain original target
C++ dispatch and are checked through instruction-byte equality; their callee
implementations remain binary-derived.

Its manifest entry declares `cpp_exceptions: false`, selecting
`-Cpp_exceptions off`. With the compiler's default setting, the 124 instruction
bytes and all three relocations matched, but the compiler also emitted an
8-byte unwind record and a 12-byte exception index entry. Those extra sections
shifted text and enlarged the converted DOL. The full-file/layout check rejected
that first link. Disabling exceptions for this unit preserves every instruction
and relocation while removing the unwanted metadata. The corrected executable
matches every original byte. This is a verified setting for this candidate,
not identification of the original project's global compiler configuration.

The manifest accepts the optional boolean `cpp_exceptions` only for C++ units.
Other units retain their existing settings. No exception bytes are masked,
removed after compilation, or copied over a linked output. Current replacements
remain code-only split units with zero associated data; units needing original
exception/static-data ownership require additional explicit work.

Fifteen focused source-link tests cover single/multiple ordered replacements,
original exclusion, invalid manifests and ranges, dependency ownership and map
placement, source-to-source call ownership, changed direct-call/SDA relocation
contracts, and C++ exception-setting validation. The six existing DOL
comparison/layout tests and eight PowerPC relocation tests also pass. The
complete three-source build passes with the explicit exception setting, and
the stop setter's exhaustive host behavior check remains active.

No replacement adds a new isolated match; all were already included in the
1,152-function survey total. Linked source coverage is now **three functions / 164
bytes**. No emulator, boot or gameplay check is included.

## What this resolves

The workspace already has a viable linker, an object order, a linker command
file, entry-point handling, relocation resolution for the binary-derived
objects, and an ELF-to-DOL conversion path that preserves the entire original
file. Reconstructing these pieces is no longer an untested prerequisite.
The new checker gives future source replacements a complete-executable
regression target rather than only an isolated function comparison.

## What remains after the first source integration

1. **Extend explicit replacement boundaries.** The stop setter, level-name lookup and application iteration now have
   independently compiled split units. Most other units are still large
   automatic spans. Recover bounded function/translation-unit splits and
   associated data ownership for each additional source replacement.
2. **Replace more units without changing addresses.** Keep the manifest-driven
   `check_source_link.py` baseline exact as the source set grows. Recompile each
   bounded unit with a target interface, substitute it in the ordered unit
   list, rerun the full link, and require complete DOL equality. Unrecovered
   units remain binary-derived during this incremental transition.
3. **Recover code and data together.** Individual function matches do not
   establish original translation-unit layout, static data, exception tables,
   vtables, constructor/destructor ordering, symbol linkage, or alignment for
   replacement units. This original-object roundtrip preserves those bytes
   through generated objects; source replacements still need to reproduce them.
4. **Recover real interfaces and broader compiler behavior.** The existing
   semantic projections and callback models are research interfaces. Exact
   matches demonstrate some useful compiler settings, but they do not identify
   the original compiler configuration for all game and SDK units. Caller and
   callee conventions must agree across a source replacement boundary.
5. **Validate execution separately.** Exact original-object bytes make the
   baseline a precise reproduction of the supplied DOL, but no emulator run,
   boot check, game image repackaging, or gameplay test was performed here.

The next useful build milestone is expanding the application-control source
set with additional independently matched routines, keeping the verified
source-to-source call and full-DOL comparison intact. Data and exception-table
ownership must be established explicitly for any replacement that needs them.
